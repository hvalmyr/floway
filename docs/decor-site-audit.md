# Аудит репозитория «floway» под второй сайт (flo-way.ru, новогоднее оформление)

Дата: 21.09.2026. Основано на ТЗ `tz-novogodniy-sait.md` v1.3, раздел 11, Этап 1
(«Аудит и план»): аудит админки и кода (п. 7.1), решение по посадочным
страницам (п. 4.2, 7.5), проверка ресурсов VPS (п. 4.3).

Документ отвечает на конкретные технические вопросы, которые ТЗ явно
адресует разработчику на этапе аудита — не на открытые вопросы к заказчику
(они остаются в разделе 13 ТЗ, здесь не переоткрываются).

## 1. Разделы админки — сверка списка из ТЗ с фактическим кодом

В ТЗ (п. 7.1) перечислено 20 разделов. По факту в `backend/internal/httpserver/`
их больше — часть не top-level пункты меню, а вложенные под уже перечисленные:

| Сущность в коде | Есть в списке ТЗ? | Что это |
|---|---|---|
| `course-faq` (`course_faq_handler.go`) | Нет | FAQ конкретного курса — вложено под `courses`, отдельного пункта меню нет |
| `page-faq` (`page_faq_handler.go`) | Нет | Заголовок/описание FAQ-блока для *фиксированных* страниц (`masterclasses`, `gift_certificate`) — см. п. 3 ниже, важно для landing-конструктора |
| `tags`, `client-comments`, `reminders` | Нет | CRM-функциональность вокруг `clients`/`leads` — комментарии к клиенту, теги, напоминания о звонке |

Последний пункт — реальная поправка к плану ТЗ: `tags`/`client-comments`/
`reminders` в п. 7.1 не упомянуты вообще, но по смыслу их нельзя отнести к
группе «скрывается» вместе с `courses`/`masterclasses` — они обслуживают
именно `leads`/`clients`, которые decor-сайту нужны как есть. Рекомендация:
отнести их к группе «переносится без изменений» (то же, что и `leads`).

Остальной список из ТЗ подтверждён 1:1 кодом — группировка на «переносится
без изменений» / «репрофилируется» (`gallery-photos`) / «скрывается»
(`courses`, `course-sections`, `course-blocks`, `masterclasses`, `teachers`,
`gift-certificates`, `gift-certificate-photos`, `clients`, `content-export`)
— технически корректна и ничего не блокирует.

Отдельно: `clients` в списке ТЗ помечен на «скрывается», но по п. 7.3 CRM по
заявкам (`leads`) остаётся — а `clients`/`tags`/`client-comments`/`reminders`
это ровно инфраструктура вокруг `leads`. Предлагаю **не скрывать** `clients`
и связанную с ним CRM-механику для decor-сайта — она нужна тому же менеджеру,
который будет обрабатывать заявки на оформление.

## 2. Справочник типов объектов и посадочные страницы (п. 4.2, 7.5)

Ключевой вопрос ТЗ: можно ли построить конструктор посадочных страниц на
`courses` + `course_blocks`, вместо разработки новой сущности с нуля.

**Разобрана фактическая схема после миграции `00016_restructure_courses_domain.sql`**
(актуальная, не оригинальная из `00002`/`00003`):

- `courses.section_id` — `NOT NULL REFERENCES course_sections`. Курс не может
  существовать без секции; секции — это группировка для *главной страницы
  школы* («Курсы флористики», «Мастер-классы» и т.п.), решаемая совсем другой
  бизнес-задачей (список курсов на главной), не «шесть независимых
  посадочных страниц под тип объекта».
- `Course` **не имеет** `meta_title`/`meta_description` — эти поля есть только
  у `BlogPost` (`backend/internal/model/model.go:388-394`). П. 7.5 явно требует
  meta title/description на каждой посадочной, значит миграция потребуется в
  любом случае, реюз `courses` её не отменяет.
- `CourseBlockWithLessons`/`Lesson` тащат за собой концепцию «урок» —
  избыточную для decor-страниц (там нет уроков, только фото/примеры работ и
  форматы услуги).
- Ни `Lead`, ни `GalleryPhoto` не имеют FK на `courses` — «единый справочник
  типов объектов, используемый и в форме заявки, и в фильтре портфолио» (п.
  7.5) пришлось бы делать поверх `courses` отдельной новой таблицей всё равно,
  той же общей сложности, что и таблица типов объектов с нуля.

**Вывод:** реюз `courses`/`course_blocks` не экономит объём миграций/кода —
пришлось бы (а) добавлять meta-поля, (б) заводить фиктивную «секцию»-контейнер
только чтобы обойти `NOT NULL section_id`, (в) всё равно создавать отдельный
справочник типов объектов для формы заявки и портфолио, (г) тащить неиспользуемую
концепцию уроков. Итоговая рекомендация — **не реюзать `courses`/`course_sections`
как есть**, а завести компактный новый набор таблиц по образцу уже
существующих паттернов проекта:

```
object_types            -- справочник: id, slug, name, sort_order, visible
                         -- (используется и в лендингах, и в лид-форме, и в фильтре портфолио)

landing_pages           -- id, object_type_id (FK), slug, h1, meta_title,
                         -- meta_description, sort_order, visible
                         -- (create/copy/rename/hide/delete из админки — п. 7.5,
                         --  без участия разработчика)

landing_page_blocks     -- id, landing_page_id (FK), image, text, sort_order
                         -- (буквальная копия паттерна course_blocks:
                         --  тот же admin CRUD-код, cover+sort_order+свободный текст —
                         --  но без lesson_count/time_length/price, они здесь не нужны)
```

FAQ на посадочной — не нужно ничего нового: `page_faq_settings`/`page_faq_items`
(миграция `00040`) уже реализует ровно эту задачу (title+description+visible+
items, привязка по текстовому ключу страницы), только `CHECK (page IN
('masterclasses','gift_certificate'))` надо заменить на `FOREIGN KEY
REFERENCES landing_pages(slug)`, поскольку страницы decor-сайта создаются
динамически, а не это фиксированный enum на два значения.

Портфолио (`gallery_photos`, миграция `00017`) сейчас — плоский `image` +
`sort_order`, без каких-либо тегов. Под п. 6 ТЗ («фильтр по типу объекта и
формату») нужны две новые колонки: `object_type_id` (FK на тот же справочник)
и `format` (`season`/`event`).

Лиды (`Lead`, `backend/internal/model/model.go:451`) сегодня **не хранят** ни
тип объекта, ни формат услуги, ни UTM/`yclid` — ни один из трёх пунктов,
которые ТЗ требует в форме и в аналитике (п. 8.1, п. 9), в модели сейчас нет.
Это отдельная миграция независимо от решения по лендингам — `object_type_id`,
`format`, `utm_source`/`utm_medium`/`utm_campaign`/`utm_content`/`utm_term`,
`yclid` на `leads`.

## 3. Переиспользуемые декоративные паттерны фронтенда

`frontend/app/components/layout/AmbientTreeBackground.vue` — уже существующий
полноэкранный фон на Three.js (цветущая ветка, `~/lib/three/flowery-branch`),
зафиксированный за карточками интерфейса, с обработкой
`prefers-reduced-motion` и деградацией на слабых устройствах уже встроенными.
Для decor-сайта это не «взять как есть» (ветка школы про цветы, не про хвою),
но это готовый, уже проверенный в проде архитектурный паттерн для ровно того
эффекта, который просит п. 5.2 («падающий снег на фоне», «лёгкая, отключаемая
анимация»): fixed transparent canvas, `pointer-events: none` на основном слое,
единая точка контроля reduced-motion. Рекомендация дизайнеру/разработчику —
строить снежный фон как параллельный компонент по этому же шаблону, а не
изобретать обработку reduced-motion/производительности заново.

## 5. Ресурсы VPS (п. 4.3, открытый вопрос №5 в ТЗ)

**Не проверено в рамках этого аудита.** Проверка требует live-подключения к
прод-VPS (`79.143.29.84`) — это действие с эффектом на боевую систему, делаю
только по отдельному подтверждению. Когда будет ок — план проверки:

```bash
ansible floway_prod -i ansible/inventory/production.yml -m shell -a "free -h && df -h /" --vault-password-file ansible/.vault_pass
```

Ориентир: второй полный стек — это ещё один Postgres, ещё один Garage, backend
и frontend-контейнер — сопоставимо по памяти с уже работающим стеком школы.
`enable_swap: true` (2G) в текущем `vars.yml` — сигнал, что машина и так не
избыточна по памяти; итоговое решение (тот же VPS / отдельный VPS) нужно
принимать по факту цифр, а не заранее.

## 6. Итог и следующий шаг

Технически декомпозиция из ТЗ (второй Nuxt-каталог, второй backend-инстанс,
отдельная inventory-группа, общий Caddy/telegram-proxy) подтверждена кодом —
блокеров нет. Единственная содержательная правка плана — не реюзать
`courses`/`course_sections` под конструктор посадочных страниц (п. 2 выше),
а завести три новых компактных таблицы, переиспользуя `page_faq_settings` и
паттерн `course_blocks` как код-шаблон, а не как таблицы напрямую.

Следующий шаг — Этап 2 (дизайн) не может начаться раньше макетов от
дизайнера/заказчика (п. 5.3); из технической части, независимо от макетов,
можно уже сейчас без риска для прод-сайта школы:

- проверить ресурсы VPS (см. п. 5, нужно подтверждение перед запуском);
- завести `frontend-decor/` и вторую inventory-группу `floway_decor_prod` как
  пустые каркасы (не влияет на прод школы, `kursfloristiki.ru` не трогается).
